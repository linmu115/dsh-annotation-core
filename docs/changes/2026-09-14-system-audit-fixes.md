# 系统审计修复：提交身份与上下文额度

本次对应系统审计 F01、F03，并实现 F05 所需的 Core 生命周期调用。版本与组合发布由部署任务统一处理。

## F01：旧回执不能确认新草稿

发送结果丢失后，如果用户改了文字或附件，而旧请求已经持久化，Core 现在先重新读取待发送引用，再为当前草稿分配新的提交身份并实际提交。当前草稿的成功与失败只由这次新提交决定。旧请求仍在排队或持久性未知时，保留当前草稿并提示稍后重试；内容未改变的重试保持原有幂等身份。

## F03：初始引用按本次请求剩余容量准备

Host 在读取初始上游问答之前，解析本轮附件，并取得当前模型的上下文容量。计算包含已有消息、当前系统提示及动态上下文、工具定义、本轮正文和附件表示、输出预留，另外保留 4096 token 安全余量。引用限额取剩余容量与模型容量 20% 的较小值。所有初始引用均计入完整序列化封装，包含标识、注释、文档、选区及转义开销。

文本使用每 UTF-8 字节一个 token 的保守估算。每个图片出现位置使用官方 provider 的 imageRequestPricing，包括工具结果中的嵌套图片；文件使用官方 fileRequestText 返回的实际只读文件句柄文字，不复制正文。普通 provider 缺少容量、系统装配不可用、图片成本未知及不支持计价的内容会阻止提交并保留草稿。Codex 的未知容量采用下述明确标注的保守模式。附件绑定只在执行器接受时消费；额度不足不会退休文件回执。

后续上游工具仍使用本轮共享累计预算，先扣除本轮已带入的初始上游内容，且重新检查请求余量。初始准备完成不会赋予工具无限读取权限。

### Codex 原生上下文准备

Core 通过 Runtime 的只读 prepareReferenceBudget 能力取得原生准备结果，不用外层会话历史冒充 Codex 内层线程用量。结果分为 new-thread、verified-thread、conservative 三种依据：新线程使用当前运行 home 下有效的官方模型目录与配置容量；复用线程要求已完成轮次的用量与新读取的线程摘要、模型及配置匹配；无法确认时按 RD07 采用保守上限，并在准备结果与诊断中明确标记 conservative。

保守模式的 8 KiB 限额覆盖完整引用序列化、来源描述和原生输入的转义开销，同时扣除实际本轮请求、系统提示、动态工具定义、输出预留及安全余量，遵守 provider 输入字节上限。这不是已测得的内层剩余容量。新线程计入完整 bootstrap、选定技能和原生 provider 输入；已确认的复用线程计入真实内层用量和本轮新增输入。后续工具仍要求本轮有效的原生用量，未放宽工具读取额度。

异步准备前记录本地会话及选择状态，在来源读取完成后、执行器预览完成且实际入队前再次检查。Runtime 同时核对模型、工作目录、配置、会话事件及最近执行身份、工具与技能描述摘要；改变后拒绝沿用旧额度并保留草稿。重复核对不重新请求 provider。无图片的提交不执行额外的模型能力探测，Codex 初始准备使用自身的定向模型查询。

配套版本为 Annotation Core 0.3.12-rc2.7、Codex Runtime 0.2.0-dev.17、Runtime Support 0.1.0-dev.9。原生终态只在已有执行记录增加数值用量与摘要，不新增历史全文快照。

## F05：结束一次预算执行

初始读取循环通过 finally 调用可选的 Maintenance endExecution，即使读取失败或取消也会结束。每次实际准备使用独立执行 ID，故失败后重新准备不会复用已结束账本；已持久提交的幂等重试不重新准备。

工具额度在内存中仅保留当前活动会话的当前轮次；turn/end、下一 turn/start、session/disposed、agent/disposed 会清理额度并通知 Maintenance。已经结束的轮次不能再次读取。Maintenance 端负责持久记账、防重放与失效运行清理，Core 保持 protocolVersion 1 及原 read DTO，通过方法存在性检测接入新能力。
